# 写作与文档维护规范

本文件负责表达、文档职责和更新条件。任务授权、安全限制和事实优先级以根目录 `AGENTS.md` 为准；工程实现要求见 `ENGINEERING_RULES.md`。

## 1. 通用表达规范

- 先给结论，再说明原因、影响和必要的验证方式。
- 使用明确对象和准确动词，一个句子尽量只表达一个主要动作或事实。
- 存在因果、转折或条件时明确说明；没有逻辑关系时不强行连接。
- 标题直接说明对象。删除空泛宣传词和缺乏对象的表达，如“赋能”“抓手”“整体优化”。
- 能直接写“查询接口”“更新状态”“检查日志”时，不用“走”“打”“接”“落”等词代替具体动作。
- 函数名、类名、变量名、文件路径、配置项、命令和错误信息保留原文。
- 在中文说明中解释英文术语时使用 `English（中文）` 格式；技术标识不强行翻译。
- 区分当前事实、正式目标、推导结论和待确认事项。未执行的检查不得写成已验证。
- 不使用没有来源的“不是 A，而是 B”对比句，不把缺乏证据的旧方案作为对照。
- 给出执行步骤时说明操作对象、前置条件与预期结果；命令从项目真实文件核对。

## 2. 文档职责

以下职责是项目文档的唯一维护规则。`README.md` 负责导航，不复制本节为第二份规范。

| 文档或位置 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| `AGENTS.md` | AI 入口、范围授权、安全、读取要求和验收约束 | 具体语言规范、个人设置、执行日志 |
| `README.md` | 项目介绍、实际目录、技术基线、环境、启动、构建、测试、发布入口和文档导航 | 当前测试结果证明、完整目标规划 |
| `docs/ENGINEERING_RULES.md` | 通用工程原则和已确认的项目专属开发规则 | 第二份执行命令表、项目状态 |
| `docs/WRITING_RULES.md` | 表达、文档职责和更新条件 | 项目功能状态、具体实施过程 |
| `docs/CURRENT_STATE.md` | 当前实际实现、重要限制、实际阶段、重大偏差和有效验证依据 | 未来目标、问题处理流水账、每次 AI 操作记录 |
| `PROJECT_PLAN.md`（可选） | 项目目标、范围、目标架构、实施阶段和项目级验收标准 | 把临时实现偏差改写成目标 |
| `docs/contracts/`（可选） | 已确认的业务、数据规则及边界 | 为错误实现修改规则、未确认草案 |
| `docs/api/`（可选） | 正式接口、参数、响应和错误契约 | 无接口影响的内部实现细节 |
| `docs/design/`（可选） | 已确认专项设计的目标、职责、边界、依赖和验收标准 | 持续追加完成时间、部署记录或实施日志 |
| `docs/audits/`（可选） | 特定日期、范围和版本的审查或验收结论及证据 | 当前规则、永远有效的状态保证 |
| `docs/archive/`（可选） | 已失效但仍有参考价值的历史文档 | 当前需求、当前状态或正式目标依据 |

可选目录只在有实际内容时创建。草案不得放入正式契约目录并冒充已确认规则；需要保留草案时按实际协作需要明确标记其未确认状态，不默认新增草案体系。

## 3. 更新触发条件

| 实际变化 | 检查或更新 |
| --- | --- |
| 已实现功能、主要结构、重要限制或实际阶段变化 | `docs/CURRENT_STATE.md` |
| 目录、环境、依赖基线、启动、测试或发布方式变化 | `README.md` |
| 项目级范围、目标架构、阶段或验收标准正式变化 | 已存在的 `PROJECT_PLAN.md` |
| 正式业务或数据规则明确变化 | 相关 `docs/contracts/`，并按入口规则同步实现和测试 |
| 接口增删，方法、路径、参数、请求、返回、状态码或错误结构变化 | 相关 `docs/api/` |
| 专项设计目标、边界、依赖或验收标准正式变化 | 对应 `docs/design/` |
| 开发规则正式变化 | `docs/ENGINEERING_RULES.md` |
| 文档职责或写作规则正式变化 | `docs/WRITING_RULES.md` |
| 任务入口、关键安全限制或读取要求变化 | `AGENTS.md` |
| 需要保存阶段验收或重大审查证据 | 按需新增有日期的 `docs/audits/` 文件 |

- 内部重构、变量改名、格式化或无项目级影响的小修复，通常不需要修改状态和规划文档。
- 当前实现偏离正式计划时，在状态文件记录重要偏差，不据此自动修改计划。
- 专项实施完成后，实际状态进入状态文件；设计文件保留目标与验收标准，不追加实施流水账。
- 没有实际变化时不更新文档，也不为了宣称“已同步”而改日期。
- 对应可选文档不存在时，不自动创建整套文档；确有必要才增加，并更新 README 导航。

## 4. 状态、审查和归档

### 4.1 当前状态

- 顶部维护初始基线、最近完整代码复核日期、可确认版本及最近局部核查范围。
- 没有执行完整复核时明确写“待确认”，不得将局部开发或测试描述为全项目已复核。
- 当前限制只保留仍然有效且有项目级影响的内容。问题修复后更新或删除对应限制。
- 验证依据记录日期、版本、范围、结果、证据位置与未验证事项，只保留支持当前结论的有效记录。
- 仓库实现与实际部署分别记录；没有检查部署时写“未核查”。

### 4.2 审查结果

- 审查记录说明日期、对象、版本、核查范围、执行方式、结论与未验证事项。
- 创建后保留当时的事实，不因后续修复覆盖原结论。确需纠错时明确标注更正内容、日期与原因。
- 不把历史审查通过当成当前版本也已通过。

### 4.3 历史归档

- 只有已失效且确有参考价值的文档才归档，不为普通修改创建历史副本。
- 归档时注明失效原因、日期和有效替代入口；没有替代文档时如实说明。
- 更新当前导航，避免读者将归档内容当成现行规则。
- 移动或移除已有文件仍需遵守入口规则的范围与授权限制。

## 5. 修改与一致性检查

- 修改已有文档前完整阅读并理解其原意，避免盲目搜索替换或批量改写。
- 当前文档只保留已确认的有效方案；直接相关且已废弃的内容删除或按需要归档。
- 检查文档与已经核实的实现、配置、契约和验证证据是否一致，不复制未经核查的旧结论。
- 同一规则或命令只维护一处，其他文件引用其位置。路径、术语和状态口径保持一致。
- 文件移动或重命名后检查入口、导航和相对链接，不保留指向不存在文件的链接。
- 使用 Markdown 时，标题与正文、列表与前文之间保留空行；表格、代码块和目录示意保持可读。
- 多人或多代理同时处理文档时按文件分工，同一个文件只由一个负责人修改，最终检查跨文件一致性。
