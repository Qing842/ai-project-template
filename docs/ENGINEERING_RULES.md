# 工程规范

本文件分为通用规范与项目专属规范。任务授权、安全限制、事实与契约优先级、子代理协作和交付要求以根目录 `AGENTS.md` 为准，不在本文件重复维护。

## 1. 通用规范

### 1.1 分析真实实现

- 从本次任务的实际入口确认调用过程、输入来源、状态变化和输出位置。
- 检查当前源码、配置与运行证据，不用项目介绍、旧版本或相似项目代替实际实现。
- 结论应对应到具体文件、类、函数、配置项、查询、测试或日志。
- 区分已经核查的事实、由证据推导的结论和仍待确认的事项。
- 不把注释中的描述、计划中的功能或未执行的测试当成当前实际行为。

### 1.2 先定位根因再修复

1. 确认现象、触发条件和预期行为。
2. 阅读真实入口和相关实现，必要时在安全环境复现。
3. 找到错误首次出现的位置，分析实际输入与状态变化。
4. 确认根因能够解释现象，不只解释某条报错。
5. 实施针对根因的最小修复，必要时增加回归测试。
6. 执行与本次修复直接相关的验证。

禁止凭经验直接修改、同时修改多个猜测原因试错、用临时分支掩盖根因或添加没有明确用途的防御代码。

### 1.3 简单、可维护的实现

- 在正确性、可读性、可测试性与可维护性之间选择最简单可行方案。
- 优先复用项目已有且职责合适的实现，不为单次任务引入新的框架或通用平台。
- 不为未确认的未来需求或极低概率场景增加依赖、状态和抽象。
- 修改前检查直接相关旧逻辑；新实现完整替代旧实现时，删除本次范围内已经失效的接口、配置、依赖和重复实现。
- 不扩大为无关清理，也不长期保留两套实现处理同一职责。
- 遵守项目已有且明确的代码风格，不混入无关格式化或大范围重命名。

### 1.4 模块边界与数据

- 明确每个模块负责的业务对象、输入、输出和允许访问的依赖。
- 调用关系尽量直接，避免无实际用途的多层转发。
- 同一个状态或业务规则确定唯一维护位置，不在多个模块分别复制。
- 区分采集原始值、转换后字段、存储状态和接口展示值，不把空值、默认值或缺失字段混为一谈。
- 涉及事务、幂等、重试、缓存和并发时，只增加解决已确认需求所必需的机制，并说明边界。
- 正式接口、业务和数据规则发生变化时，按 `AGENTS.md` 与 `WRITING_RULES.md` 处理，不以内部实现替代契约。

### 1.5 注释与错误处理

- 注释说明代码职责、输入来源、调用时机、参数与返回值用途，以及非显然的业务限制。
- 复杂协议、字段转换、加解密、验签、一次性凭证和敏感数据处理需要解释关键约束；日志不得包含秘密。
- 不用“处理数据”“执行操作”等空泛注释替代业务说明，也不逐行复述直观代码。
- 修改行为时同步直接相关注释，删除已经失效的描述。
- 明确错误是否需要向调用方返回、重试、记录或终止。不静默吞掉影响正确性的异常。
- 日志提供足够的定位信息，避免重复记录同一异常及输出完整敏感载荷。

### 1.6 第三方依赖

- 从当前配置或锁文件确认实际版本，检查该版本官方文档、公开接口或源码。
- 不根据博客、旧文章或旧版本经验判断当前行为。
- 新增或升级依赖前，说明具体用途、兼容影响和必要验证；不因新版本存在就扩大为升级任务。
- 不能核查当前版本行为时，明确说明不确定性，不虚构接口或参数。

### 1.7 验证要求

- 代码变更执行相关测试或构建；接口变更核对正式契约和实际响应。
- 缺陷修复优先增加能覆盖触发条件的测试，避免只检查正常路径。
- 影响输入或返回结构时验证字段、类型、空值和错误结果；影响数据时验证隔离环境中的实际读写行为。
- 影响交互、布局或主题时，检查实际页面及本次涉及的状态。
- 不降低测试断言、跳过失败检查或修改期望值来迎合错误实现。
- 全量验证仅在变更风险、依赖范围或项目要求确有需要时执行，不把全项目扫描作为每次小修改的默认动作。
